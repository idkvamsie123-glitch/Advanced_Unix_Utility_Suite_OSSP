PROJECT OVERVIEW

Introduction & Concept Definition

UnixSuite is a modular, menu-driven command-line toolkit developed in standard C99 that bridges the gap between theoretical operating system concepts and actual kernel execution.

🐧 POSIX Interfaces

Directly interfaces with Linux kernel system calls (C interfaces) rather than high-level third-party libraries.

🧩 Modular Design

Decoupled modules with dedicated header (.h) declarations and implementation (.c) units.

🔍 Internal Telemetry

Embedded [INTERNAL WORKING] tracing that explains kernel transitions for every user command.

1. System Info (uname/sysconf) 2. Process Manager (fork/exec/wait) 3. VFS & Inodes (open/read/stat) 4. IPC & Pipes (pipe/read/write) 5. Memory Analysis (/proc/self) 6. Concurrency (pthreads/mutex)

PROJECT GOALS

Primary Project Objectives

1. System Telemetry

Extract OS release, kernel architecture, CPU topology, and page metrics via uname() and sysconf().

2. Process Control

Demonstrate address space cloning via fork(), binary loading via execlp(), and reap via waitpid().

3. VFS Operations

Perform byte stream I/O (open, read, close) and inspect physical inode metadata using stat().

4. IPC via Pipes

Establish unidirectional FIFO kernel channels between parent and child processes using pipe().

5. Signal Dispatch

Install reliable signal handlers with sigaction() and dispatch software interrupts via kill().

6. Memory Maps

Parse /proc/self/status and /proc/self/maps to measure VmSize, VmRSS, and virtual segments.

7. Thread Sync

Implement POSIX threads (pthreads) and prove mutual exclusion using pthread_mutex_t.

8. Modular C

Maintain clean software architecture, automated compilation via Makefile, and POSIX conformance.

MODULES 1 & 3

System Information & File Management

🖥️ 1. System Information

  • uname(&info): Fills struct utsname with OS name, release (e.g., 6.6 WSL2), version, and machine architecture (x86_64).
  • sysconf(_SC_NPROCESSORS_ONLN): Retrieves total active CPU cores for multi-core scheduling.
  • sysconf(_SC_PAGESIZE): Queries standard hardware memory page size (4096 Bytes).

📁 2. File System (VFS & Inodes)

  • stat(path, &st): Inspects inode metadata without reading file content (size, octal permissions 0644, UID/GID).
  • open(..., O_CREAT | O_EXCL): Atomically creates new files and returns an integer File Descriptor (FD).
  • read() / close(): Reads raw byte buffers and safely frees the FD slot in the process table.
🗣️ Speaker Note (Slide 8): "Here we contrast system information with file management. `uname()` and `sysconf()` query live kernel parameters, while `stat()` extracts physical inode metadata and `open()/read()` demonstrate low-level file descriptor stream I/O."
MODULE 2 DEEP DIVE

Process Creation & Lifecycle Management

  • 1. fork() — Address Space Cloning
    Duplicates parent process. Returns 0 to child and Child PID to parent.
  • 2. execlp() — Binary Image Overlay
    Replaces child process text & data segments with new binary (e.g. echo).
  • 3. waitpid() — Synchronization & Status
    Parent blocks until child terminates, inspecting WEXITSTATUS(status) to reap zombie.
// Complete fork-exec-wait flow pid_t pid = fork(); if (pid == 0) { // In Child Process execlp("echo", "echo", "[Child] Executed!", NULL); _exit(1); } else { // In Parent Process waitpid(pid, &status, 0); if (WIFEXITED(status)) { printf("Exit Code: %d\n", WEXITSTATUS(status)); } }
🗣️ Speaker Note (Slide 9): "It is crucial to distinguish process creation from program execution. `fork()` creates a new process by cloning the parent, while `exec()` replaces the memory image of that process with a new program. The parent uses `waitpid()` to avoid leaving zombie processes."
MODULE 4 DEEP DIVE

Inter-Process Communication via Anonymous Pipes

🚰 Pipe Communication Mechanism

  • pipe(pipefd[2]): Allocates a unidirectional FIFO buffer in kernel ring memory.
  • pipefd[1] (Write End): Child closes read end (0) and writes message into pipe buffer.
  • pipefd[0] (Read End): Parent closes write end (1) and reads bytes synchronously.
  • Zero Disk Overhead: Transfers data entirely in memory across process boundaries.
// Pipe IPC Implementation int pipefd[2]; pipe(pipefd); // [0]=Read, [1]=Write if (fork() == 0) { close(pipefd[0]); write(pipefd[1], "Hello Parent", 13); close(pipefd[1]); _exit(0); } close(pipefd[1]); read(pipefd[0], buffer, sizeof(buffer)); close(pipefd[0]); waitpid(pid, NULL, 0);
🗣️ Speaker Note (Slide 10): "Anonymous pipes provide unidirectional byte streaming between related processes. The child writes into `pipefd[1]`, and the parent reads from `pipefd[0]`. Unused file descriptors are closed to ensure proper end-of-file signaling."
MODULE 4 PART B

Signal Handling & Asynchronous Notifications

⚡ POSIX Signal Architecture

  • Signals vs Pipes: Signals are asynchronous interrupts that notify a process of an event rather than transmitting large data streams.
  • sigaction(): Installs reliable signal handler for SIGUSR1 with clear signal masks.
  • kill(pid, SIGUSR1): Sends signal to target PID (does not necessarily terminate the process).
  • volatile sig_atomic_t: Ensures atomic read/write of shared signal flag variables.
// Signal Registration & Dispatch static volatile sig_atomic_t flag = 0; void handle_sigusr1(int sig) { flag = 1; // Atomic signal handler update } struct sigaction sa; sa.sa_handler = handle_sigusr1; sigemptyset(&sa.sa_mask); sigaction(SIGUSR1, &sa, NULL); // Send signal to self kill(getpid(), SIGUSR1);
🗣️ Speaker Note (Slide 11): "Signals allow processes to handle asynchronous events. We use `sigaction()` rather than the legacy `signal()` API for portable, reliable handler registration, and declare our handler flags as `volatile sig_atomic_t` for thread-safe atomicity."
MODULE 5 DEEP DIVE

Virtual Memory Architecture & /proc Telemetry

📐 Linux Virtual Address Space Layout

Kernel Space (0xFFFF8000...)
Stack (Grows Downward ↓) [Local Variables]
Memory Mapping Segment (Shared Libs, libc.so)
Heap (Grows Upward ↑) [malloc / brk]
BSS & Data Segments (Globals)
Text Segment (Executable Machine Code [r-xp])

📊 /proc/self/status Metrics

  • VmSize vs VmRSS: VmSize is the total allocated virtual space; VmRSS (Resident Set Size) is the actual physical RAM loaded.
  • VmPeak: Peak virtual memory consumption during process lifetime.
  • VmData & VmStk: Exact virtual memory dedicated to data segments and stack frames.
  • /proc/self/maps: Lists address ranges, page permissions (r-xp, rw-p), and mapped file offsets.
🗣️ Speaker Note (Slide 12): "Our memory module inspects `/proc/self/status` and `/proc/self/maps`. Crucially, we emphasize that virtual memory (VmSize) and physical resident memory (VmRSS) are not interchangeable—VmRSS represents the exact physical memory pages currently mapped in hardware RAM."
MODULE 6 DEEP DIVE

Multithreading, Concurrency & Mutex Synchronization

🧵 POSIX Threads & Shared Memory

  • Shared Address Space: Unlike processes, threads created with pthread_create() share the same heap and global memory.
  • Critical Section: Incrementing shared_counter++ involves three CPU instructions: Read ➔ Modify ➔ Write.
  • Race Conditions: Unsynchronized thread interleaving causes missed increments.
  • Mutex Locking: pthread_mutex_lock() forces mutual exclusion, guaranteeing exactly 200,000 increments.
// Worker Function with Mutex Protection void *worker(void *arg) { for (int i = 0; i < 100000; i++) { pthread_mutex_lock(&counter_mutex); shared_counter++; // Critical Section pthread_mutex_unlock(&counter_mutex); } return NULL; } // Result: Expected 200,000 | Actual 200,000
🗣️ Speaker Note (Slide 13): "In multithreading, multiple threads share a single process's memory. When two threads concurrently increment a counter without synchronization, a race condition occurs. Enclosing the increment inside a mutex lock guarantees mutual exclusion and 100% data integrity."
